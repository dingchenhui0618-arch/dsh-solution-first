# Solution first — 先选路径，再动手

## 为什么需要这一步

从零实现是最贵的路径，也是最容易产出「没人用的代码」的路径。
大多数任务已经有现成解：本机装过的工具、项目已有的依赖、标准库、
或开源生态里活跃的项目。

**默认从零写是错的；默认先找是应该的。**

## 何时用

- 任何非平凡任务：新功能、新项目、新脚本、重构、排障
- 需求听起来「随便做一下」，但你说不出验收标准时
- 你发现自己正准备「先写个骨架看看」

## 何时不用

- 只改一两个文件、目标明确的修补
- 纯粹的读代码、检索、回答问题
- 用户明确说过「就手写一个，不要引依赖」

不用时，也要在回复里用**一句话**说明为什么跳过。

## 第一步：造候选（按代价从低到高）

1. **本机已装能力** —— 先看这台机器上已经有什么：agent skill 目录、已配置的 CLI、
   本地常驻服务、项目里的既有脚本。已经付过成本的东西优先。
2. **项目内既有实现** —— 同一仓库里是不是已经有类似的函数 / 模块 / 模式。
   **在仓库里搜，不要靠记忆。**
3. **标准库与已有依赖** —— 项目依赖清单里已经有的，不要新增平行依赖。
4. **社区** —— GitHub、npm、PyPI、skills 注册表。

搜索时用**任务语义**搜（「把 PDF 转成可搜索的 markdown」），
不要用你打算写的函数名搜 —— 你的命名不会出现在别人的 README 里。

## 第二步：评估候选

对每个进入决赛圈的候选逐条给结论，不要笼统说「看起来不错」：

| 维度 | 要回答什么 |
|---|---|
| 适配度 | 它解决的问题和我们的问题是不是同一个？差多少？ |
| 活跃度 | 最近提交 / 发版时间；issue 有没有维护者回应 |
| 体积与依赖 | 引入它会拖进来多少东西？值不值？ |
| 许可证 | 能不能用在当前场景（商用 / 闭源 / 分发方式） |
| 可局部采用 | 能不能只抄一个函数、一个思路，而不是整套引入 |
| 退出成本 | 以后要换掉它，代价大不大 |

**「可局部采用」经常才是正确答案** —— 借鉴一段实现，比引一个依赖更好。

## 第三步：决定并记录

回复的第一段必须包含三件事：

- 选了哪条路（直接用 / 改造 / 局部借鉴 / 自建）
- 为什么选它
- **放弃了什么，以及为什么放弃**

没有第三点，就说明你没有真的做过对比。

## 验收标准先于代码

动手前先说清「怎么算做完了」。说不出验收标准 = 还没准备好开始。

标准不清楚时：**停下来问用户**，不要先写代码再对齐。
常见坏味道：「先把框架搭起来」「先写个初版看看」。

## 停止条件

- 搜了两轮、候选都不合格 → 自建，并说明为什么不复用
- 需求本身不清楚 → 停下来问，不要用「先做一版」代替对齐
- 只有用户明确要求「快速原型」时，才允许无验收标准地写代码，
  并在交付时标注这是原型、缺哪些标准

## 常见错误

- **拿文档当事实。** README 说它支持 X，不等于它真的支持 X。看代码，或跑一遍。
- **用函数名搜社区。** 见第一步第 4 条。
- **只找一个候选就开工。** 没有对比，就没有「最省力」可言。
- **把「我引入了库」当产出。** 引依赖也是成本，要说清它换来了什么。
- **小改动不说明就跳过。** 跳过是允许的，但要给理由；不给理由等于没做判断。
- **把「我搜过了」当结论。** 搜索要留下候选名和评估结果，否则无法复核。
